# Контекст практики: "Учебная рабочая среда"

Этот документ содержит сводную информацию по требованиям к практике и правилам создания проектов (MVP). Он заменяет необходимость чтения всех исходных PDF и MD документов из папки `practise-docs`.

## 1. Введение и общие цели
- **Длительность:** Спринт 2 недели.
- **Цель:** Создать MVP (минимально жизнеспособный продукт) одного из модулей системы "учебной рабочей среды". 
- **Концепция:** Вместо единой монолитной платформы разрабатывается набор независимых, слабо связанных инструментов (помощников), каждый из которых выполняет свою узкую продуктовую функцию.

## 2. Организационные требования и отчетность
В рамках практики действует жесткий формат отчетности:
- **Ежедневные заметки:** Во время работы над практикой необходимо вести регулярные ежедневные заметки в формате `.md`. В них описываются планы на день (задачи формулируются строго по методике **SMART** со слотами от 1 до 4 часов, максимум 8), а также фиксируется проделанная работа. По-хорошему, каждая завершенная задача в заметках должна подтверждаться артефактом работы (ссылкой на написанный код, pull request, схему или задачу в трекере).
- **Защита:** Перед защитой все накопленные ежедневные заметки из `.md` файла необходимо перенести в сводный Word-документ (в формате `Ежедневные_Записи_ФамилияИмя.docx`).

## 3. Архитектурные требования к MVP
- **Слабая связанность (Loose coupling):** Модули общаются между собой через независимые контракты: файловые папки, CLI, веб-хуки, REST API таск-трекеров (Redmine, Nextcloud) и Git-хуки.
- **Никаких "велосипедов" и больших платформ:** Важно использовать существующие инструменты (трекеры, git, файловые хранилища). Запрещено писать полноценные монолитные системы (например, нельзя писать свой стандартный LRS-сервер с нуля).
- **Паспорт модуля:** Проект должен включать паспорт модуля в формате **MD (`.md`)**, оформленный строго по шаблону из файла `пример_описания_модуля.md`. В паспорте описываются: позиционирование, решаемая задача, гипотеза, пользователи, границы MVP, интеграции и метрики успеха.
- **Полевые испытания:** Разработка MVP заканчивается проведением реальных испытаний (на команде или мок-данных) с обязательным замером заявленных метрик успеха (например, сколько времени сэкономил модуль, сколько решений зафиксировано и т.д.).

## 4. Интеграция через xAPI (События-свидетельства)
Система отслеживает прогресс не через ручные отчеты, а через автоматические "свидетельства", которые генерируют модули.
- **Формат xAPI:** События записываются в формате `Кто (Actor) -> Что сделал (Verb) -> С чем (Object) -> В каком контексте (Context)`.
- **Контекст события:** Содержит ссылки на подтверждающие артефакты (pull request, сгенерированный pdf, запись в трекере).
- **Гибкость хранения:** xAPI — очень гибкий формат, который имеет всего несколько обязательных полей. По этой причине модули-хранилища извлекают только основные обязательные поля, а все остальное содержимое сохраняют в сыром JSON, чтобы не терять данные.
- **Как это работает:** Любой отработавший модуль генерирует и отправляет (например, по REST) JSON-событие в легковесное хранилище (например, модуль `Evidence Locker`). Позже модули-визуализаторы (как `Skill-matrix`) читают эти события, чтобы построить красивую доску навыков.

## 5. Каталог доступных модулей (Для MVP)
Ниже перечислены концепты модулей, один из которых студент может выбрать для реализации MVP:

**Модули для учащихся (разработка и прогресс):**
1. **Transcriptor + Tracker:** Переводит аудио встреч в текст, достает решения и ставит задачи в трекер.
2. **Guide:** Бот-наставник (работает, например, через git hooks), который проверяет качество коммитов перед отправкой.
3. **Progressor:** Мониторит проект (репозиторий) и автоматически превращает написанный код или тесты в подтверждение освоенных навыков.
4. **White-list-breaker:** Помощник для старта заблокированных задач. Предлагает сформулировать триггер ("если-то") и делает первый микро-шаг.
5. **Skill-matrix:** Визуализирует матрицу навыков на основе реальных свидетельств, собранных другими модулями.
6. **Evidence Locker:** Хранилище, принимающее стандартизированные события-свидетельства (xAPI) от других модулей.

**Модули для преподавателей (работа с курсами):**
1. **Course-Connector:** Сравнивает курсы по компетенциям, чтобы найти дублирование или пробелы.
2. **Course CLI:** Утилита для создания структуры новых курсов и валидации их метаданных (через `init`, `validate`, `report`).
3. **Slide-deck-generator:** Автоматически превращает Markdown-планы уроков в черновики PDF-презентаций.
4. **Speech-vs-Plan:** Сравнивает аудио-расшифровку реальной лекции с изначальным планом и показывает, что было упущено.

## 6. Структура исходной документации (`practise-docs/`)
Если потребуется детальная спецификация для реализации, ниже описано назначение каждого исходного файла из папки `practise-docs`:
- `едежневные_записи.md` — общие правила для ведения отчетов и критерии SMART.
- `модули_системы.md` — концепция "учебной рабочей среды", общая архитектура и краткое описание каждого модуля.
- `пример_описания_модуля.md` — пример того, как должен выглядеть подробный Паспорт модуля (на примере *Transcriptor-Tracker*). Используется как шаблон.
- `course-cli.pdf` — детальная спецификация преподавательского модуля *Course CLI*.
- `evidence-locker.pdf` — детальная спецификация хранилища событий *Evidence Locker*.
- `slides-generator.md` — детальная спецификация модуля *Slide-deck-generator*.
- `speech-vs-plan.pdf` — детальная спецификация модуля *Speech-vs-Plan*.
- `system-vision.pdf` — общее видение (вижн) системы, дополняющее документ с архитектурой.
- `transcriptor-tracker.pdf` — детальная спецификация модуля *Transcriptor-Tracker* (аналогична `пример_описания_модуля.md`, но в PDF формате).
- `white-sheet-breaker.pdf` — детальная спецификация студенческого помощника *White-list-breaker*.
